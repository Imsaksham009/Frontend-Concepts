## Start With the Problem — Why Promises Were Invented

You already know how to use Promises. But understanding **why they were invented** and **what problem they fundamentally solve** is what makes the internals click.

Before Promises, asynchronous JavaScript was handled entirely with callbacks. And callbacks worked — until you needed to sequence multiple async operations:

```javascript
// The Callback Hell Problem — also called "Pyramid of Doom"
getUser(userId, function(err, user) {
    if (err) return handleError(err);
    
    getProfile(user.id, function(err, profile) {
        if (err) return handleError(err);
        
        getOrders(profile.id, function(err, orders) {
            if (err) return handleError(err);
            
            getOrderDetails(orders[0].id, function(err, details) {
                if (err) return handleError(err);
                
                // Finally have what you need — 4 levels deep
                // Error handling duplicated at every level
                // Cannot reuse, cannot compose, cannot reason about
                render(user, profile, orders, details);
            });
        });
    });
});
```

Three fundamental problems with this:

**Inversion of Control** — You hand your callback to someone else's function and *trust* them to call it correctly, call it once, not swallow errors. You've lost control of your own code's execution.

**Error handling is duplicated** — Every level needs its own error check. Miss one and errors silently disappear.

**No composability** — You cannot take two async operations and combine them cleanly. Everything is deeply nested and tightly coupled.

Promises solve all three. They give you back **control of your own code's execution flow** while keeping async operations manageable.

## What a Promise Actually IS — The Internal State Machine

This is what most explanations skip. A Promise is not magic — it's a **state machine** wrapped around a value that doesn't exist yet.

Internally, every Promise object has exactly three pieces of state:

```
[[PromiseState]]  — 'pending' | 'fulfilled' | 'rejected'
[[PromiseResult]] — the resolved value OR rejection reason
[[PromiseReactions]] — list of .then()/.catch() handlers waiting
```

These are internal slots — you cannot access them directly on the object. But everything a Promise does is just transitions between these states and processing the reactions list.

The state machine has strict rules:

```
                    resolve(value)
                ┌──────────────────→ FULFILLED (locked, [[PromiseResult]] = value)
                │
PENDING ────────┤
                │
                └──────────────────→ REJECTED  (locked, [[PromiseResult]] = reason)
                    reject(reason)
```

**Three rules that are absolute:**
1. A Promise starts in `pending`
2. It can transition to `fulfilled` OR `rejected` — exactly once
3. Once settled (fulfilled or rejected), it **never changes state again**

This immutability is fundamental. Once a Promise resolves with a value, that value is permanent. This is what makes Promises trustworthy — you can attach `.then()` handlers a minute later and you'll still get the same result.

```javascript
const p = new Promise((resolve) => {
    resolve(42);      // state: pending → fulfilled, result: 42
    resolve(100);     // IGNORED — already settled
    reject('error');  // IGNORED — already settled
});

// Even after the Promise is settled, you can still attach handlers
// They will fire asynchronously with the already-settled value
setTimeout(() => {
    p.then(v => console.log(v)); // 42 — works even though p settled long ago
}, 5000);
```

## The `Promise` Constructor — Internal Mechanics

When you write `new Promise((resolve, reject) => { ... })`, here is exactly what happens inside the engine:

**Step 1:** A new Promise object is created with `[[PromiseState]] = 'pending'`, `[[PromiseResult]] = undefined`, `[[PromiseReactions]] = []`.

**Step 2:** The engine creates two internal functions — `resolve` and `reject` — that are bound to this specific Promise object. These are the only things that can change the Promise's state.

**Step 3:** Your executor function is called **synchronously** — immediately, right now, on the call stack — with those two functions as arguments.

**Step 4:** Your executor runs. If it throws, the Promise is automatically rejected with the thrown error.

```javascript
console.log('1 — before Promise');

const p = new Promise((resolve, reject) => {
    console.log('2 — executor runs SYNCHRONOUSLY');
    // This runs right now, on the call stack
    
    resolve(42); // queues resolution as microtask
    
    console.log('3 — after resolve call');
    // resolve() doesn't stop execution — it just schedules the resolution
});

console.log('4 — after Promise constructor');

p.then(v => console.log('5 — then handler:', v));

console.log('6 — after .then()');

// Output order:
// 1 — before Promise
// 2 — executor runs SYNCHRONOUSLY
// 3 — after resolve call
// 4 — after Promise constructor
// 6 — after .then()
// 5 — then handler: 42   ← microtask, runs after current synchronous code
```

This is a critical interview point. The executor is synchronous. Only the `.then()` handlers are asynchronous (microtasks).

## How `resolve` Works Internally — The Resolution Procedure

When you call `resolve(value)` inside a Promise, it doesn't immediately settle the Promise. It triggers what the spec calls the **Promise Resolution Procedure** — a specific algorithm:

```
resolve(value) is called:
    │
    ├── Is value the same Promise? → reject with TypeError (can't resolve with itself)
    │
    ├── Is value a Promise (or thenable)?
    │       YES → attach a handler to value
    │             when value fulfills → fulfill this Promise with same value
    │             when value rejects  → reject this Promise with same reason
    │             (this is how Promise chains propagate)
    │
    └── Is value a plain value?
            YES → fulfill this Promise with value
                  schedule all .then() handlers as microtasks
```

The thenable check is what makes Promises interoperable. A "thenable" is any object with a `.then()` method — even from third-party libraries. This is why you can mix Promises from different sources:

```javascript
// Resolving with another Promise — chain propagates
const p1 = new Promise(resolve => {
    resolve(new Promise(resolve2 => {
        setTimeout(() => resolve2(42), 1000);
    }));
});

// p1 is NOT immediately fulfilled with the inner Promise
// p1 WAITS for the inner Promise to settle
// After 1 second, p1 fulfills with 42

p1.then(v => console.log(v)); // 42 (after 1 second)
```

## `.then()` Internals — The Mechanism Behind Chaining

`.then()` is the heart of Promises. Understanding what it does internally unlocks everything about chaining.

**`.then(onFulfilled, onRejected)` does exactly three things:**

1. Registers `onFulfilled` and `onRejected` as reaction handlers on the current Promise
2. Creates and returns a **brand new Promise** (let's call it `nextPromise`)
3. When the current Promise settles, runs the appropriate handler as a **microtask**, and uses the return value to resolve `nextPromise`

```javascript
const p = Promise.resolve(1);

const p2 = p.then(value => {
    // This handler runs as a microtask
    // Whatever this returns becomes the resolution of p2
    return value + 1; // p2 resolves with 2
});

const p3 = p2.then(value => {
    return value * 10; // p3 resolves with 20
});

p3.then(value => console.log(value)); // 20
```

The key insight: **each `.then()` creates a new Promise**. You're not modifying the original Promise — you're creating a chain of Promises where each one resolves based on what the previous handler returned.

### What the Handler's Return Value Determines

This is where it gets precise. What you return from a `.then()` handler determines how `nextPromise` is resolved:

```javascript
// Case 1: Return a plain value → nextPromise resolves with that value
Promise.resolve(1)
    .then(v => v + 1)           // returns 2
    .then(v => console.log(v)); // 2

// Case 2: Return a Promise → nextPromise WAITS for it
Promise.resolve(1)
    .then(v => new Promise(resolve => setTimeout(() => resolve(v * 10), 1000)))
    .then(v => console.log(v)); // 10 (after 1 second)

// Case 3: Return nothing → nextPromise resolves with undefined
Promise.resolve(1)
    .then(v => { console.log(v); }) // returns undefined
    .then(v => console.log(v));     // undefined

// Case 4: Throw an error → nextPromise is REJECTED with the error
Promise.resolve(1)
    .then(v => { throw new Error('Something went wrong'); })
    .catch(err => console.log(err.message)); // 'Something went wrong'

// Case 5: Return a rejected Promise → nextPromise is rejected
Promise.resolve(1)
    .then(v => Promise.reject('oops'))
    .catch(err => console.log(err)); // 'oops'
```

## The Microtask Queue — How Promise Handlers Are Scheduled

This connects Promises directly to the event loop we covered earlier. Understanding this timing is critical for interviews.

When a Promise settles, its handlers are **not called immediately**. They are scheduled as **microtasks** — placed in the microtask queue to run after the current synchronous code completes but before the next macrotask.

```javascript
console.log('1 - sync start');

Promise.resolve()
    .then(() => console.log('3 - microtask 1'))
    .then(() => console.log('5 - microtask 2'));

Promise.resolve()
    .then(() => console.log('4 - microtask 3'));

console.log('2 - sync end');

// Exact output order:
// 1 - sync start
// 2 - sync end
// 3 - microtask 1   ← microtask queue drains
// 4 - microtask 3   ← second .then of first chain hasn't queued yet!
// 5 - microtask 2   ← now this queues and runs
```

Notice the order — `microtask 1` and `microtask 3` run first because they were both queued when the synchronous code finished. `microtask 2` only gets queued AFTER `microtask 1` runs (because the second `.then()` only creates its Promise after the first `.then()` handler executes).

This is the precise internal sequence for each microtask turn:

```
Promise settles
    → look at [[PromiseReactions]]
    → for each reaction: schedule handler as microtask
    → clear [[PromiseReactions]]

Microtask runs:
    → call the handler with [[PromiseResult]]
    → take the return value
    → run the Promise Resolution Procedure on nextPromise
    → if nextPromise now has reactions, schedule THEM as microtasks
```

## Error Propagation — How Rejection Travels Through Chains

This is the most important thing to understand about Promise chains for real-world code.

When a Promise is rejected and there's no `onRejected` handler in the current `.then()`, the rejection **passes through** to the next Promise in the chain. It keeps propagating until something handles it or it reaches the end of the chain unhandled.

```javascript
Promise.reject(new Error('original error'))
    .then(v => v + 1)        // no onRejected — rejection passes through
    .then(v => v * 2)        // no onRejected — rejection passes through
    .then(v => v + 100)      // no onRejected — rejection passes through
    .catch(err => {
        // Finally caught here — all intermediate .then() were skipped
        console.log(err.message); // 'original error'
        return 'recovered'; // returning a value RECOVERS the chain
    })
    .then(v => console.log(v)); // 'recovered' — chain continues normally
```

The internal mechanism: when `.then()` receives a rejected Promise and has no `onRejected` handler, the `nextPromise` it creates is simply rejected with the same reason. This propagation continues until a `.catch()` (which is just `.then(null, onRejected)`) handles it.

### Recovery and Re-Rejection

```javascript
// Recovering from rejection
Promise.reject('error')
    .catch(err => {
        console.log('caught:', err);
        return 'recovered'; // return value → chain continues as fulfilled
    })
    .then(v => console.log('after recovery:', v)); // 'after recovery: recovered'

// Re-throwing to keep rejecting
Promise.reject('error')
    .catch(err => {
        console.log('logged:', err);
        throw err; // re-throw → chain stays rejected
    })
    .catch(err => console.log('caught again:', err)); // 'caught again: error'

// catch followed by then — the then runs normally
Promise.reject('error')
    .catch(err => 'default value') // handles rejection, returns normal value
    .then(v => console.log(v));    // 'default value' — fully recovered

// The error in a THEN handler rejects nextPromise
Promise.resolve('ok')
    .then(v => {
        throw new Error('then threw!'); // creates rejection
    })
    .then(v => console.log('never runs'))
    .catch(err => console.log(err.message)); // 'then threw!'
```

## Promise Chaining — The Complete Internal Picture

Let's trace through a real async chain completely, step by step, to cement the internal picture:

```javascript
function fetchUser(id) {
    return fetch(`/api/users/${id}`)
        .then(response => {
            if (!response.ok) throw new Error(`HTTP ${response.status}`);
            return response.json();
        });
}

function fetchUserPosts(user) {
    return fetch(`/api/posts?userId=${user.id}`)
        .then(r => r.json());
}

fetchUser(1)
    .then(user => {
        console.log('Got user:', user.name);
        return fetchUserPosts(user); // return Promise — chain waits
    })
    .then(posts => {
        console.log('Got posts:', posts.length);
        return posts.filter(p => p.published); // return value — chain continues
    })
    .then(published => {
        console.log('Published posts:', published.length);
    })
    .catch(err => {
        // Catches errors from ANY step above
        console.error('Something failed:', err.message);
    })
    .finally(() => {
        // Runs regardless of success or failure
        // Does NOT receive the value/reason as argument
        // Does NOT change the value/reason (unless throws)
        hideLoadingSpinner();
    });
```

Internally the engine creates this chain of Promises:

```
p1 (fetch returns this)
    ↓ .then() → creates p2
p2 (resolves when response.json() resolves with user)
    ↓ .then() → creates p3
p3 (resolves when fetchUserPosts resolves)
    ↓ .then() → creates p4
p4 (resolves with filtered array)
    ↓ .then() → creates p5
p5 (resolves with undefined — last then returns nothing)
    ↓ .catch() → creates p6
p6 (resolves normally if no error, or handles rejection)
    ↓ .finally() → creates p7
p7 (always runs, preserves the value/reason from p6)
```

Each arrow represents a microtask that runs when the previous Promise settles.

## `.finally()` — Internal Mechanics

`.finally()` has specific internal behavior that's worth knowing precisely:

```javascript
// finally does NOT receive the value
Promise.resolve(42)
    .finally(value => {
        console.log(value); // undefined — finally gets NO argument
        return 100;          // return value is IGNORED
    })
    .then(v => console.log(v)); // 42 — original value passes through

// finally does NOT change the rejection reason
Promise.reject('error')
    .finally(() => {
        return 'ignored'; // ignored — rejection passes through
    })
    .catch(err => console.log(err)); // 'error' — original reason

// EXCEPTION: if finally throws, it OVERRIDES the value/reason
Promise.resolve(42)
    .finally(() => {
        throw new Error('finally error!'); // this DOES change the chain
    })
    .catch(err => console.log(err.message)); // 'finally error!' — original 42 lost

// EXCEPTION: if finally returns a rejected Promise, it overrides
Promise.resolve(42)
    .finally(() => Promise.reject('override!'))
    .catch(err => console.log(err)); // 'override!'
```

The internal rule: `.finally()` passes through the settled value/reason unless its callback throws or returns a rejected Promise.

## Promise Static Methods — Internals and Behavior

### `Promise.resolve()` and `Promise.reject()`

These are not just shortcuts — they have specific internal behavior:

```javascript
// Promise.resolve() with a non-thenable value — creates already-fulfilled Promise
const p1 = Promise.resolve(42);
// Immediately fulfilled. But .then() still runs as microtask, not synchronously

// Promise.resolve() with a Promise — returns that SAME Promise (not a wrapper)
const original = new Promise(resolve => resolve(1));
const same = Promise.resolve(original);
console.log(same === original); // true! — no wrapping, same object returned

// Promise.resolve() with a thenable (non-Promise) — wraps it
const thenable = { then(resolve) { resolve(42); } };
const wrapped = Promise.resolve(thenable);
// wrapped is a NEW Promise that follows the thenable

// Promise.reject() — ALWAYS creates a new rejected Promise
// Even if you pass a Promise to it, it rejects WITH that Promise as the reason
const p = Promise.reject(new Error('failed'));
p.catch(err => console.log(err.message)); // 'failed'
```

### `Promise.all()` — Internal Mechanics

`Promise.all` takes an array of Promises and returns a new Promise that:
- **Fulfills** when ALL input Promises fulfill — with an array of their values in the same order
- **Rejects immediately** when ANY input Promise rejects — with that rejection reason

The internal mechanism maintains a counter and an array, using the index to preserve order regardless of settlement order:

```javascript
// Internal mechanism — this is essentially what Promise.all does
function promiseAll(promises) {
    return new Promise((resolve, reject) => {
        if (promises.length === 0) return resolve([]);
        
        const results = new Array(promises.length);
        let resolvedCount = 0;
        
        promises.forEach((promise, index) => {
            Promise.resolve(promise) // handle non-Promise values
                .then(value => {
                    results[index] = value; // preserve order via index
                    resolvedCount++;
                    
                    if (resolvedCount === promises.length) {
                        resolve(results); // all done
                    }
                })
                .catch(reject); // first rejection immediately rejects all
        });
    });
}
```

Critical behavior to understand:

```javascript
// Order is guaranteed — not based on settlement time
const p1 = new Promise(r => setTimeout(() => r('slow'), 3000));
const p2 = new Promise(r => setTimeout(() => r('fast'), 100));
const p3 = new Promise(r => setTimeout(() => r('medium'), 1000));

Promise.all([p1, p2, p3]).then(results => {
    console.log(results); // ['slow', 'fast', 'medium'] — index order, not time order
});
// Takes 3 seconds total — waits for the slowest

// Short-circuit on first rejection
const p4 = Promise.resolve(1);
const p5 = Promise.reject('error');
const p6 = new Promise(r => setTimeout(() => r(3), 5000)); // never awaited

Promise.all([p4, p5, p6])
    .then(console.log)
    .catch(err => console.log('Rejected:', err)); // 'Rejected: error'
// p6 never resolves/rejects — it's just abandoned
// This can cause MEMORY LEAKS in real code if p6 holds resources

// Non-Promise values are wrapped in Promise.resolve()
Promise.all([1, 'hello', Promise.resolve(3)])
    .then(console.log); // [1, 'hello', 3]
```

### `Promise.allSettled()` — Never Rejects

`Promise.allSettled` waits for ALL Promises to settle regardless of whether they fulfill or reject. Returns an array of descriptor objects:

```javascript
const promises = [
    Promise.resolve(1),
    Promise.reject('error'),
    Promise.resolve(3)
];

Promise.allSettled(promises).then(results => {
    console.log(results);
    // [
    //   { status: 'fulfilled', value: 1 },
    //   { status: 'rejected', reason: 'error' },
    //   { status: 'fulfilled', value: 3 }
    // ]
    
    // Common pattern — separate successes and failures
    const fulfilled = results.filter(r => r.status === 'fulfilled');
    const rejected  = results.filter(r => r.status === 'rejected');
});

// Real world use — batch operations where partial failure is acceptable
async function processUsers(userIds) {
    const results = await Promise.allSettled(
        userIds.map(id => updateUser(id))
    );
    
    const succeeded = results
        .filter(r => r.status === 'fulfilled')
        .map(r => r.value);
        
    const failed = results
        .filter(r => r.status === 'rejected')
        .map(r => r.reason);
    
    console.log(`${succeeded.length} succeeded, ${failed.length} failed`);
    return { succeeded, failed };
}
```

### `Promise.any()` — First Success

`Promise.any` resolves with the first fulfilled Promise. Only rejects if ALL Promises reject (with an `AggregateError`):

```javascript
// Resolves with first fulfillment — ignores rejections
Promise.any([
    Promise.reject('error 1'),
    new Promise(r => setTimeout(() => r('second!'), 500)),
    new Promise(r => setTimeout(() => r('third!'), 100)),
]).then(v => console.log(v)); // 'third!' — fastest fulfillment

// Only rejects if ALL reject
Promise.any([
    Promise.reject('err 1'),
    Promise.reject('err 2'),
    Promise.reject('err 3'),
]).catch(err => {
    console.log(err instanceof AggregateError); // true
    console.log(err.errors); // ['err 1', 'err 2', 'err 3']
    console.log(err.message); // 'All promises were rejected'
});

// Real world — try multiple sources, use fastest successful one
async function fetchWithFallback(url) {
    return Promise.any([
        fetch(`https://cdn1.example.com${url}`),
        fetch(`https://cdn2.example.com${url}`),
        fetch(`https://cdn3.example.com${url}`)
    ]);
    // Gets data from whichever CDN responds first successfully
    // If one CDN is down, others cover it automatically
}
```

### `Promise.race()` — First to Settle (Fulfilled OR Rejected)

Resolves or rejects with whichever Promise settles first — regardless of whether it fulfills or rejects:

```javascript
// First to settle wins — fulfilled or rejected
Promise.race([
    new Promise(r => setTimeout(() => r('slow'), 3000)),
    new Promise(r => setTimeout(() => r('fast'), 100)),
]).then(v => console.log(v)); // 'fast'

// Rejection can also win the race
Promise.race([
    new Promise((_, r) => setTimeout(() => r('fast error'), 100)),
    new Promise(r => setTimeout(() => r('slow'), 3000)),
]).catch(err => console.log(err)); // 'fast error'

// The most important real-world use — TIMEOUT PATTERN
function withTimeout(promise, ms) {
    const timeout = new Promise((_, reject) =>
        setTimeout(() => reject(new Error(`Timed out after ${ms}ms`)), ms)
    );
    
    return Promise.race([promise, timeout]);
}

// Usage — if fetchUser takes more than 5 seconds, timeout wins
withTimeout(fetchUser(1), 5000)
    .then(user => console.log(user))
    .catch(err => console.log(err.message)); // 'Timed out after 5000ms'
```

## Promise Anti-Patterns — What Goes Wrong Internally

Knowing these is critical for interviews and for real-world code.

### Anti-Pattern 1 — The Forgotten Return

```javascript
// WRONG — breaks the chain
function getUser(id) {
    return fetch(`/api/users/${id}`)
        .then(response => {
            response.json(); // forgot return! returns undefined
        })
        .then(user => {
            console.log(user); // undefined — data lost!
        });
}

// CORRECT
function getUser(id) {
    return fetch(`/api/users/${id}`)
        .then(response => response.json()) // return!
        .then(user => console.log(user));
}
```

### Anti-Pattern 2 — Promise Constructor Anti-Pattern (Deferred)

Wrapping something that's already a Promise in `new Promise()`:

```javascript
// WRONG — unnecessary wrapping, loses error propagation
function getUser(id) {
    return new Promise((resolve, reject) => {
        fetch(`/api/users/${id}`)
            .then(r => r.json())
            .then(resolve)    // if .then() throws, reject is never called!
            .catch(reject);
    });
}

// CORRECT — fetch already returns a Promise, just chain it
function getUser(id) {
    return fetch(`/api/users/${id}`)
        .then(r => r.json());
}
```

### Anti-Pattern 3 — Swallowing Errors

```javascript
// WRONG — empty catch swallows errors silently
fetch('/api/data')
    .then(processData)
    .catch(err => {}); // error disappears — you'll never know what failed

// CORRECT — always handle or re-throw
fetch('/api/data')
    .then(processData)
    .catch(err => {
        console.error('Failed to fetch data:', err);
        // Either handle it properly or re-throw
        throw err; // or return a default value
    });
```

### Anti-Pattern 4 — Unhandled Rejection

```javascript
// WRONG — rejected Promise with no .catch()
const p = Promise.reject(new Error('oops'));
// Node.js will emit 'unhandledRejection' warning
// Browser will show console error
// Future Node.js versions will CRASH the process

// CORRECT — always handle rejections
const p = Promise.reject(new Error('oops'))
    .catch(err => console.error(err));

// Or at the global level — last resort
process.on('unhandledRejection', (reason, promise) => {
    console.error('Unhandled rejection:', reason);
});

window.addEventListener('unhandledrejection', event => {
    console.error('Unhandled rejection:', event.reason);
});
```

### Anti-Pattern 5 — Nested Promises (Callback Hell Returns)

```javascript
// WRONG — nesting defeats the purpose of Promises
getUser(1)
    .then(user => {
        getPosts(user.id)   // missing return!
            .then(posts => {
                getComments(posts[0].id)
                    .then(comments => {
                        // Back to pyramid of doom
                        render(user, posts, comments);
                    });
            });
    });

// CORRECT — flat chain with returns
getUser(1)
    .then(user => {
        // Store user for later use — closure captures it
        return getPosts(user.id)
            .then(posts => ({ user, posts })); // pass both forward
    })
    .then(({ user, posts }) => {
        return getComments(posts[0].id)
            .then(comments => ({ user, posts, comments }));
    })
    .then(({ user, posts, comments }) => {
        render(user, posts, comments);
    });

// EVEN BETTER — use async/await (covered next)
async function renderPage() {
    const user     = await getUser(1);
    const posts    = await getPosts(user.id);
    const comments = await getComments(posts[0].id);
    render(user, posts, comments);
}
```

## Promise Timing Edge Cases — What Trips People Up in Interviews

```javascript
// Edge Case 1: Already-resolved Promise still runs .then() asynchronously
const p = Promise.resolve(42);
console.log('before .then()');
p.then(v => console.log('then:', v));
console.log('after .then()');

// Output:
// before .then()
// after .then()
// then: 42   ← ALWAYS async, even for already-resolved Promises

// Edge Case 2: .then() callbacks don't prevent garbage collection
// The Promise chain is kept alive by references in the chain itself
// If you lose the reference to the chain, it CAN be garbage collected

// Edge Case 3: Multiple .then() on same Promise — all run
const base = Promise.resolve(1);
base.then(v => console.log('first:', v));  // 1
base.then(v => console.log('second:', v)); // 1
base.then(v => v * 2).then(v => console.log('third:', v)); // 2
// All three handlers attached to same base Promise
// All run as separate microtasks in attachment order

// Edge Case 4: resolve() with pending Promise — chain waits
let resolve2;
const inner = new Promise(r => resolve2 = r);
const outer = Promise.resolve(inner); // outer waits for inner

outer.then(v => console.log('outer resolved:', v));
// Nothing logged yet...

resolve2(100); // resolve inner Promise
// Now: "outer resolved: 100"
```

## The `MyPromise` Implementation from Your PDF — With Full Understanding

Now that you understand all the internals, the `MyPromise` implementation from your PDF makes complete sense. Let me walk through **why** each part is written the way it is:

```javascript
const STATE = {
    PENDING:   'PENDING',
    FULFILLED: 'FULFILLED',
    REJECTED:  'REJECTED'
};

class MyPromise {
    constructor(executorFn) {
        this.state    = STATE.PENDING;    // [[PromiseState]]
        this.value    = undefined;         // [[PromiseResult]]
        this.handlers = [];               // [[PromiseReactions]]
        
        try {
            // Executor runs SYNCHRONOUSLY — just like native Promise
            executorFn(this._resolve, this._reject);
        } catch(error) {
            // Any throw in executor rejects the Promise
            this._reject(error);
        }
    }
    
    // Arrow functions so 'this' is always the Promise instance
    // regardless of how resolve/reject are called
    _resolve = (value) => {
        this.updateResult(value, STATE.FULFILLED);
    }
    
    _reject = (error) => {
        this.updateResult(error, STATE.REJECTED);
    }
    
    updateResult(value, state) {
        // setTimeout makes resolution ASYNCHRONOUS — microtask simulation
        // Real Promises use microtask queue; we use setTimeout as approximation
        setTimeout(() => {
            // ONCE SETTLED — ignore further resolve/reject calls
            if (this.state !== STATE.PENDING) return;
            
            // Handle resolving with another Promise (thenable check)
            if (value instanceof MyPromise) {
                // Wait for the inner Promise to settle
                // Pass our own resolve/reject so we follow it
                return value.then(this._resolve, this._reject);
            }
            
            // Update state and value
            this.value = value;
            this.state = state;
            
            // Process all waiting handlers
            this.executeHandlers();
        }, 0);
    }
    
    then(onSuccess, onFailure) {
        // Returns NEW Promise — this is what makes chaining work
        return new MyPromise((resolve, reject) => {
            this.addHandlers({
                onSuccess(value) {
                    if (!onSuccess) return resolve(value); // pass through
                    try {
                        resolve(onSuccess(value)); // resolve with handler's return
                    } catch(error) {
                        reject(error); // throw in handler → rejection
                    }
                },
                onFailure(value) {
                    if (!onFailure) return reject(value); // pass rejection through
                    try {
                        resolve(onFailure(value)); // handled rejection → resolved!
                    } catch(error) {
                        reject(error);
                    }
                }
            });
        });
    }
    
    addHandlers(handlers) {
        this.handlers.push(handlers);
        // Execute immediately if already settled
        // This handles the case where .then() is called AFTER resolution
        this.executeHandlers();
    }
    
    executeHandlers() {
        // Don't run handlers until settled
        if (this.state === STATE.PENDING) return;
        
        this.handlers.forEach(handler => {
            if (this.state === STATE.FULFILLED) {
                handler.onSuccess(this.value);
            } else {
                handler.onFailure(this.value);
            }
        });
        
        // Clear after execution — handlers run exactly once
        this.handlers = [];
    }
    
    catch(onFailure) {
        // .catch() is just .then() with no success handler
        return this.then(null, onFailure);
    }
    
    finally(callback) {
        return new MyPromise((resolve, reject) => {
            let val;
            let wasRejected;
            
            this.then(
                value => { wasRejected = false; val = value; return callback(); },
                err   => { wasRejected = true;  val = err;   return callback(); }
            )
            .then(() => {
                // callback's return value ignored — unless it returns rejected Promise
                if (!wasRejected) return resolve(val);
                return reject(val);
            })
            .catch(err => reject(err)); // if callback throws, override with new error
        });
    }
}
```

Every line maps directly to the internal behavior we discussed:
- `handlers = []` → `[[PromiseReactions]]`
- `setTimeout` → microtask scheduling approximation
- `instanceof MyPromise` check → thenable resolution procedure
- `then` returning new Promise → chaining mechanism
- `resolve(onSuccess(value))` → handler return value resolves nextPromise
- `handlers = []` after execute → each handler runs exactly once

## The Complete Mental Model

A Promise is a **state machine** with three states. Once it leaves `pending`, it's permanently settled.

The **executor runs synchronously**. Only `.then()` handlers are asynchronous — always scheduled as microtasks.

**`.then()` always returns a new Promise**. This new Promise resolves based on what the handler returns — plain value, another Promise, or a throw. This is the single mechanism that makes chaining work.

**Rejection propagates** through the chain until something handles it. An unhandled rejection at the end is a real problem.

The **microtask queue** processes ALL Promise callbacks before the next macrotask. This is why Promises feel "instant" compared to `setTimeout`, and why they can starve the macrotask queue if handlers keep generating new microtasks.

**`Promise.all`** is concurrent with order preservation.
**`Promise.allSettled`** never short-circuits.
**`Promise.any`** is the opposite of `Promise.all` — first success.
**`Promise.race`** is pure speed — first to settle, success or failure.

Understanding these internals means you can predict exactly what any Promise-based code will do, in what order, and why — which is exactly what senior JavaScript interviews test.
