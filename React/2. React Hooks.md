# React Hooks — FE Interview Deep Dive

---

# PART 1 — Hooks: Basic

## 1. `useState`

```jsx
const [count, setCount] = useState(0);
```

**Core mechanics to know:**
- `useState` returns `[value, setter]`. Calling the setter **schedules a re-render**, it doesn't mutate the value in place.
- React **batches** state updates (in event handlers always; since React 18, also inside promises, timeouts, and native event handlers via automatic batching).
- Functional updates (`setCount(prev => prev + 1)`) should be used whenever the new state depends on the old state, because multiple state updates in the same batch/tick can otherwise read a stale closed-over value.

```jsx
// BAD — can lose updates if called multiple times in the same batch
setCount(count + 1);
setCount(count + 1); // still uses stale `count`, ends up +1, not +2

// GOOD
setCount(prev => prev + 1);
setCount(prev => prev + 1); // correctly +2
```

- Lazy initialization: pass a **function** to `useState` when the initial value is expensive to compute — it only runs once, on mount.

```jsx
const [data, setData] = useState(() => expensiveComputation());
```

**Interview soundbite:**
> "`useState` updates are asynchronous and batched, and the setter doesn't merge objects like `this.setState` did in class components — you must spread the previous object yourself. Always prefer the functional updater form when the new value depends on the previous one."

## 2. `useEffect` (Dependency Array Pitfalls, Cleanup)

```jsx
useEffect(() => {
  const id = setInterval(() => console.log('tick'), 1000);
  return () => clearInterval(id); // cleanup
}, [/* deps */]);
```

**Three dependency-array modes:**
| Array | Behavior |
|---|---|
| Omitted | Runs after **every** render |
| `[]` | Runs once, after initial mount |
| `[a, b]` | Runs after mount, and whenever `a` or `b` changes (referential/`Object.is` comparison) |

**Common pitfalls (favorite interview territory):**

1. **Missing dependencies** — using a variable inside the effect but not listing it causes **stale closures** (see Advanced section). ESLint's `exhaustive-deps` rule catches this.
2. **Object/array/function dependencies causing infinite loops** — a new object/array/function literal is created every render, so if it's in the deps array, the effect re-runs every render, and if that effect also sets state, you get an infinite loop.
```jsx
// BAD — options is a new object every render → effect runs every render
const options = { limit: 10 };
useEffect(() => { fetchData(options); }, [options]);

// GOOD — memoize or move primitive values into deps directly
useEffect(() => { fetchData({ limit }); }, [limit]);
```
3. **Cleanup runs before the *next* effect and on unmount** — not just on unmount. This matters for effects tied to changing props (e.g., re-subscribing to a new chat room ID should first unsubscribe from the old one).
4. **Effect ordering** — cleanup of the *previous* render's effect runs before the *new* effect of the current render.

**Interview soundbite:**
> "The dependency array isn't a performance knob you tune freely — it's a correctness contract. Every reactive value read inside the effect belongs in it. If that causes too-frequent re-runs, the fix is to restructure the effect or memoize the dependency, not to lie to the linter by omitting it."

## 3. `useRef`

Two main use cases:

**a) DOM references:**
```jsx
const inputRef = useRef(null);
useEffect(() => { inputRef.current.focus(); }, []);
return <input ref={inputRef} />;
```

**b) Mutable value that persists across renders WITHOUT causing re-renders:**
```jsx
const renderCount = useRef(0);
useEffect(() => { renderCount.current += 1; });
```

**Key distinction from `useState`:**
| | `useState` | `useRef` |
|---|---|---|
| Triggers re-render on change | Yes | No |
| Value persists across renders | Yes | Yes |
| Mutable directly (`.current = x`) | No (must use setter) | Yes |

**Interview soundbite:**
> "`useRef` gives you a mutable box that survives re-renders but doesn't participate in the render cycle — it's the escape hatch for imperative needs like focusing a DOM node, storing a timer ID, or tracking a previous value, without triggering extra renders."

**Common trap:** *"Why shouldn't I read/write `ref.current` during render (outside effects/handlers)?"* Because it makes the component impure and can produce inconsistent results, especially under concurrent rendering where render can be paused/retried.

## 4. `useContext`

```jsx
const ThemeContext = createContext('light');

function App() {
  return (
    <ThemeContext.Provider value="dark">
      <Toolbar />
    </ThemeContext.Provider>
  );
}

function Toolbar() {
  const theme = useContext(ThemeContext); // "dark"
  return <div>{theme}</div>;
}
```

**Core mechanics:**
- `useContext` subscribes the component to the nearest matching `Provider` above it in the tree.
- If no `Provider` is found, it falls back to the `defaultValue` passed to `createContext`.
- **Any component consuming a context re-renders whenever the Provider's `value` changes** (covered in depth in the State Management section below).

**Interview soundbite:**
> "`useContext` solves prop drilling for data that many components at different depths need — theme, auth user, locale — but it's not a general state management replacement; it re-renders every consumer on any value change, so it works best for infrequently-changing, broadly-needed data."

# PART 2 — Hooks: State Management

## 5. `useReducer`

```jsx
function reducer(state, action) {
  switch (action.type) {
    case 'increment': return { count: state.count + 1 };
    case 'decrement': return { count: state.count - 1 };
    default: throw new Error('Unknown action');
  }
}

function Counter() {
  const [state, dispatch] = useReducer(reducer, { count: 0 });
  return (
    <>
      <button onClick={() => dispatch({ type: 'increment' })}>+</button>
      {state.count}
    </>
  );
}
```

**When to prefer `useReducer` over `useState`:**
- State is complex/structured (multiple sub-values that update together).
- Next state depends on previous state in non-trivial ways.
- Many event handlers mutate the same state in different ways — centralizing transition logic in a reducer improves testability and readability.
- You want to pass `dispatch` down instead of many individual setters (dispatch has a **stable identity**, so it doesn't cause unnecessary re-renders or need to be in dependency arrays).

**Interview soundbite:**
> "`useReducer` is essentially a mini-Redux local to a component — it centralizes 'what happened' (actions) and 'how state changes' (reducer) separately from 'when' (dispatch calls), which scales better than a pile of `useState` calls when state transitions get complex or interrelated."

---

## 6. Context API + `useContext` (Avoiding Prop Drilling)

**Prop drilling** = passing props through many intermediate components that don't use them, just to get data to a deeply nested child.

```jsx
// Prop drilling (bad at scale)
<A user={user}><B user={user}><C user={user}><D user={user} /></C></B></A>

// Context (avoids drilling)
<UserContext.Provider value={user}>
  <A><B><C><D /></C></B></A>
</UserContext.Provider>
// D reads: const user = useContext(UserContext);
```

**Setting up Context properly (pattern interviewers like to see):**
```jsx
const UserContext = createContext(null);

export function UserProvider({ children }) {
  const [user, setUser] = useState(null);
  const value = useMemo(() => ({ user, setUser }), [user]); // see pitfall #7
  return <UserContext.Provider value={value}>{children}</UserContext.Provider>;
}

export function useUser() {
  const ctx = useContext(UserContext);
  if (!ctx) throw new Error('useUser must be used within UserProvider');
  return ctx;
}
```

**Interview soundbite:**
> "Context solves the *plumbing* problem of prop drilling, but it's not a performance-free global store — every value change re-renders every consumer, so for high-frequency updates (like form state or animation values), a dedicated state library or colocated state is usually better."

## 7. Context Re-render Pitfalls (Splitting Context to Avoid Over-rendering)

**The core problem:** Every component calling `useContext(MyContext)` re-renders whenever the Provider's `value` **reference** changes — even if the specific field that component reads didn't change.

```jsx
// BAD — value is a brand-new object every render → ALL consumers re-render every render
function App() {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState('light');
  return (
    <AppContext.Provider value={{ user, setUser, theme, setTheme }}>
      <Children />
    </AppContext.Provider>
  );
}
```

**Fixes (know several — this is a favorite senior-level question):**

1. **Memoize the context value:**
```jsx
const value = useMemo(() => ({ user, setUser, theme, setTheme }), [user, theme]);
```
This helps only if consumers actually re-render on referential inequality of the *whole* object — it does NOT stop re-renders when `user` or `theme` themselves change, which is often unavoidable/expected. It mainly prevents *extra unrelated* re-renders (e.g., a parent re-rendering for unrelated reasons recreating the object).

2. **Split into multiple contexts** — separate frequently-changing values from rarely-changing ones, so consumers only subscribe to what they actually need:
```jsx
<UserContext.Provider value={user}>
  <ThemeContext.Provider value={theme}>
    <Children />
  </ThemeContext.Provider>
</UserContext.Provider>
```
Now a component that only reads `ThemeContext` won't re-render when `user` changes.

3. **Split state and dispatch into separate contexts** (common with `useReducer` + Context):
```jsx
<StateContext.Provider value={state}>
  <DispatchContext.Provider value={dispatch}> {/* dispatch is stable, never changes */}
    <Children />
  </DispatchContext.Provider>
</StateContext.Provider>
```
Components that only need to *dispatch* actions (e.g., a button) never re-render on state changes.

4. **Move state down / colocate** — if only a subtree needs certain state, don't lift it into a context available to the whole app.

5. **External state libraries (Zustand, Jotai, Redux with selectors)** — these use **selector-based subscriptions**, so a component only re-renders when the *specific slice* it selects changes, sidestepping the "any change re-renders all consumers" limitation of Context entirely. This is the real answer when Context-splitting isn't enough.

**Interview soundbite:**
> "Context doesn't do selective/partial subscriptions — it's all-or-nothing per Provider. `useMemo` on the value object stops redundant re-creation, but the real fix for over-rendering is splitting contexts by change-frequency/concern, or reaching for a selector-based state library once you outgrow Context's granularity."

# PART 3 — Hooks: Advanced

## 8. `useMemo`

```jsx
const sortedList = useMemo(() => expensiveSort(list), [list]);
```

- Memoizes a **computed value**, recalculating only when dependencies change.
- Use for genuinely expensive computations (heavy sorting/filtering/transformations) or to preserve **referential equality** of an object/array so it doesn't break `React.memo` on children or trigger downstream `useEffect`s unnecessarily.

**Pitfall:** Don't wrap trivial computations in `useMemo` — the memoization bookkeeping itself has a cost, and can hurt readability for negligible gain.

---

## 9. `useCallback`

```jsx
const handleClick = useCallback(() => {
  doSomething(id);
}, [id]);
```

- Memoizes a **function reference** across renders, changing only when dependencies change.
- `useCallback(fn, deps)` is functionally equivalent to `useMemo(() => fn, deps)`.
- Primary use case: preventing a memoized child (`React.memo`) from re-rendering due to receiving a "new" function prop every render, or keeping a stable reference for a `useEffect` dependency.

**Interview trap:** *"If I wrap every function in `useCallback`, is that always good practice?"*
> No. Without a memoized child or a dependency-array use case, `useCallback` adds overhead (storing the closure, comparing deps) for zero benefit — the function would just be re-created either way with no downstream cost. Use it purposefully, not reflexively.

---

## 10. `React.memo`

```jsx
const ExpensiveChild = React.memo(function ExpensiveChild({ data }) {
  return <div>{data.name}</div>;
});
```

- Higher-order component that **shallow-compares props** and skips re-rendering if they're all reference-equal (or `===` for primitives) to the previous render.
- Only helps if the parent is passing **stable** references for object/array/function props — otherwise `React.memo` still re-renders every time because a new object/function is "different" every render (this is exactly why `useMemo`/`useCallback` pair with `React.memo`).
- Custom comparison: `React.memo(Component, (prevProps, nextProps) => boolean)` for deep-equality needs (use sparingly — deep comparison has its own cost).

**Interview soundbite:**
> "`React.memo`, `useMemo`, and `useCallback` work as a team: `memo` skips re-render on stable props, but the props need to actually *be* stable, which is what `useMemo`/`useCallback` provide for objects/arrays/functions passed down."

---

## 11. `useLayoutEffect` vs `useEffect`

| | `useEffect` | `useLayoutEffect` |
|---|---|---|
| Timing | Runs **asynchronously**, after the browser paints | Runs **synchronously**, after DOM mutations but **before** the browser paints |
| Blocks paint? | No | Yes |
| Use case | Data fetching, subscriptions, logging — anything that doesn't need to read/adjust layout before the user sees it | Measuring DOM (`getBoundingClientRect`), synchronously adjusting layout/scroll position to avoid visual flicker |

**Classic example needing `useLayoutEffect`:** measuring a tooltip's size and repositioning it before the user sees it in the wrong place — if you used `useEffect`, the user would briefly see a flash of the mispositioned tooltip.

**Interview soundbite:**
> "Default to `useEffect`. Reach for `useLayoutEffect` only when you must read or mutate the DOM synchronously before paint to avoid a visible flicker — like measuring an element and repositioning it. It's the exception, not the default, because it blocks the browser from painting."

## 12. `useImperativeHandle` + `forwardRef`

Used when a parent needs to call **imperative methods** on a child component (not just get its DOM node).

```jsx
const FancyInput = forwardRef((props, ref) => {
  const inputRef = useRef(null);

  useImperativeHandle(ref, () => ({
    focus: () => inputRef.current.focus(),
    clear: () => { inputRef.current.value = ''; },
  }));

  return <input ref={inputRef} {...props} />;
});

function Parent() {
  const fancyRef = useRef(null);
  return (
    <>
      <FancyInput ref={fancyRef} />
      <button onClick={() => fancyRef.current.focus()}>Focus</button>
    </>
  );
}
```

- `forwardRef` lets a functional component receive a `ref` from its parent (refs aren't passed as regular props by default).
- `useImperativeHandle` customizes **what** the parent's ref actually exposes — instead of exposing the raw DOM node, you expose a curated API (`focus`, `clear`, etc.), hiding internal implementation details.

**Interview soundbite:**
> "This pair exists for the rare case where a parent genuinely needs to *command* a child imperatively — like triggering focus, scroll, or an animation — rather than just passing data down via props. It should be the exception; most component communication should stay declarative."

**Note:** As of React 19, `ref` can be passed as a regular prop to function components, making `forwardRef` unnecessary in newer codebases — but interviewers at companies on React 18 or earlier will still expect you to know `forwardRef`.

## 13. `useTransition` / `useDeferredValue` (Concurrent React)

Both let you **mark updates as lower priority**, so urgent updates (like typing in an input) aren't blocked by expensive re-renders.

**`useTransition`:**
```jsx
const [isPending, startTransition] = useTransition();

function handleChange(e) {
  setInput(e.target.value); // urgent — updates immediately
  startTransition(() => {
    setSearchResults(filterHugeList(e.target.value)); // non-urgent — can be interrupted
  });
}
```
- `isPending` lets you show a loading indicator while the transition is in flight.
- The transition update can be **interrupted** by a more urgent update (e.g., the user typing another character).

**`useDeferredValue`:**
```jsx
const deferredQuery = useDeferredValue(query);
const results = useMemo(() => filterHugeList(deferredQuery), [deferredQuery]);
```
- Similar goal, but instead of wrapping a state *setter*, you defer a *value* — React will render with the old value first (keeping the UI responsive) and re-render with the new one once it's ready, without blocking urgent updates.

**When to use which:**
- `useTransition` — when **you control the state update** causing the slow render (you can wrap the `setState` call).
- `useDeferredValue` — when you **receive a value** (e.g., a prop) and can't control how it's set, but want to prevent it from blocking urgent rendering.

**Interview soundbite:**
> "Both are part of Concurrent React's priority model — they let React interrupt a low-priority, expensive re-render to handle a high-priority one first, like keeping a text input responsive while a big filtered list renders in the background."

## 14. Stale Closures (Common Gotcha Across `useEffect`/`useCallback`/`useState`)

**What it is:** A function created during one render "closes over" the variables as they existed **at that render**. If that function is called later (e.g., from a timer, event listener, or async callback) without being recreated, it sees **outdated (stale)** values.

**Classic example:**
```jsx
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      console.log(count); // always logs 0 — stale closure!
    }, 1000);
    return () => clearInterval(id);
  }, []); // empty deps → effect (and its closure) never recreated

  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}
```
The interval's callback closes over `count` as it was (`0`) on the first render, and since the effect never re-runs (`[]` deps), it never sees updated values.

**Fixes:**
1. **Functional updater** (best when you don't actually need to *read* the value, just update based on previous state):
```jsx
setInterval(() => setCount(c => c + 1), 1000); // always correct, no stale read
```
2. **Add the value to the dependency array** (if you truly need to *read* the current value inside):
```jsx
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, [count]); // recreates interval each time count changes
```
3. **`useRef` to always hold the latest value** (avoids recreating the effect/interval while still reading fresh values):
```jsx
const countRef = useRef(count);
useEffect(() => { countRef.current = count; }, [count]);
useEffect(() => {
  const id = setInterval(() => console.log(countRef.current), 1000);
  return () => clearInterval(id);
}, []);
```

**Interview soundbite:**
> "Stale closures happen because a callback captures variables by value at the time it was created, not the DOM/state at the time it's invoked. The exhaustive-deps lint rule exists specifically to catch this — the fix is either to include the missing dependency, use a functional state update, or hold the latest value in a ref."

# PART 4 — Custom Hooks

*Custom hooks are just regular functions that call other hooks and start with `use`. Interviewers ask you to write these to test whether you understand the underlying hooks, not just to test memorization.*

## 15. `useDebounce`

Delays updating a value until the user has stopped changing the input for a specified duration — classic use case: search-as-you-type without hammering an API on every keystroke.

```jsx
function useDebounce(value, delay = 500) {
  const [debouncedValue, setDebouncedValue] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => setDebouncedValue(value), delay);
    return () => clearTimeout(timer); // cancel if value changes before delay elapses
  }, [value, delay]);

  return debouncedValue;
}

// Usage:
const debouncedSearch = useDebounce(searchTerm, 300);
useEffect(() => { fetchResults(debouncedSearch); }, [debouncedSearch]);
```

**Interview point:** The cleanup function is the whole trick — every keystroke schedules a new timeout AND cancels the previous one, so only the last one (after the user pauses) actually fires.

## 16. `useFetch`

```jsx
function useFetch(url, options) {
  const [state, setState] = useState({ data: null, loading: true, error: null });

  useEffect(() => {
    const controller = new AbortController();
    setState({ data: null, loading: true, error: null });

    fetch(url, { ...options, signal: controller.signal })
      .then(res => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return res.json();
      })
      .then(data => setState({ data, loading: false, error: null }))
      .catch(err => {
        if (err.name !== 'AbortError') {
          setState({ data: null, loading: false, error: err });
        }
      });

    return () => controller.abort(); // cancel in-flight request on unmount/url change
  }, [url]);

  return state;
}
```

**Interview points to raise proactively:**
- **Race conditions:** if `url` changes rapidly, an older, slower request could resolve *after* a newer one and overwrite fresher data — the `AbortController` cleanup prevents this.
- Mention that in real codebases, **React Query / SWR / RTK Query** are preferred over hand-rolled `useFetch` because they add caching, deduplication, retries, and background refetching — but knowing how to build one from scratch shows you understand what those libraries solve.

## 17. `useLocalStorage`

```jsx
function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {
    try {
      const stored = window.localStorage.getItem(key);
      return stored !== null ? JSON.parse(stored) : initialValue;
    } catch {
      return initialValue;
    }
  });

  useEffect(() => {
    try {
      window.localStorage.setItem(key, JSON.stringify(value));
    } catch (err) {
      console.error('Failed to persist to localStorage', err);
    }
  }, [key, value]);

  return [value, setValue];
}

// Usage:
const [theme, setTheme] = useLocalStorage('theme', 'light');
```

**Interview points:**
- Lazy initializer (`() => ...`) avoids reading `localStorage` on every render — only on mount.
- Wrap in try/catch — `localStorage` can throw (private browsing mode, storage quota exceeded, SSR environments where `window` doesn't exist).
- Bonus (senior-level): syncing across tabs via the `storage` event listener.

## 18. `useThrottle` (Bonus)

Unlike debounce (waits for a pause), throttle ensures a value/function updates **at most once per interval**, useful for scroll/resize handlers.

```jsx
function useThrottle(value, interval = 500) {
  const [throttledValue, setThrottledValue] = useState(value);
  const lastRan = useRef(Date.now());

  useEffect(() => {
    const timer = setTimeout(() => {
      if (Date.now() - lastRan.current >= interval) {
        setThrottledValue(value);
        lastRan.current = Date.now();
      }
    }, interval - (Date.now() - lastRan.current));

    return () => clearTimeout(timer);
  }, [value, interval]);

  return throttledValue;
}
```

**Debounce vs Throttle — the classic interview distinction:**
> "Debounce delays execution until activity *stops* for a period (good for search input). Throttle guarantees execution happens *at most once* per fixed interval regardless of how much activity occurs (good for scroll/resize handlers where you want regular updates, not just a final one)."

## 19. `usePrevious` (Bonus)

Captures the value of a variable **from the previous render** — useful for comparing current vs previous props/state (e.g., detecting a transition, animating based on direction of change).

```jsx
function usePrevious(value) {
  const ref = useRef();
  useEffect(() => {
    ref.current = value; // runs AFTER render, so during render ref still holds the old value
  });
  return ref.current;
}

// Usage:
function Counter({ count }) {
  const prevCount = usePrevious(count);
  return <div>Now: {count}, Before: {prevCount}</div>;
}
```

**Interview point (this trips people up):** Why does this work? Because the `useEffect` (no deps array → runs after every render) updates `ref.current` **after** the render/return has already happened, so during any given render, `ref.current` still reflects the *previous* render's value — the update to "current" happens after React reads it for that render's output.

## Quick-Reference Cheat Sheet

| Hook | One-liner |
|---|---|
| `useState` | Local state; batched, async updates; use functional form for updates based on prior state |
| `useEffect` | Side effects after paint; deps array is a correctness contract, not a perf knob |
| `useRef` | Mutable value across renders, no re-render on change; DOM refs |
| `useContext` | Subscribe to nearest Provider; re-renders on any value change |
| `useReducer` | Centralized state transitions for complex/interrelated state |
| Context splitting | Separate contexts by change-frequency to limit re-render blast radius |
| `useMemo` | Memoize expensive **values** |
| `useCallback` | Memoize **function references** (pairs with `React.memo`) |
| `React.memo` | Skip re-render on shallow-equal props |
| `useLayoutEffect` | Sync, pre-paint DOM reads/writes (avoid flicker); default to `useEffect` instead |
| `useImperativeHandle`+`forwardRef` | Expose a curated imperative API to a parent via ref |
| `useTransition`/`useDeferredValue` | Deprioritize expensive updates without blocking urgent ones |
| Stale closures | Captured-at-render-time variables; fix via functional updates, correct deps, or refs |
| `useDebounce` | Delay until input activity pauses |
| `useThrottle` | Cap update frequency to at most once per interval |
| `useFetch` | Data fetching + abort on unmount/url change to avoid race conditions |
| `useLocalStorage` | Sync state with `localStorage`, lazy-init + try/catch |
| `usePrevious` | Track prior render's value via ref + effect-after-render timing |
