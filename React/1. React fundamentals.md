# React Fundamentals — FE Interview Guide

---

## 1. Virtual DOM

**What it is:** A lightweight in-memory JS representation of the actual DOM. React keeps a tree of plain JS objects mirroring the UI structure.

**Why it exists:** Direct DOM manipulation is slow because it triggers layout, paint, and reflow. React batches updates by first computing changes on the Virtual DOM (cheap, in-memory) and then applying only the necessary changes to the real DOM.

**Interview soundbite:**
> "The Virtual DOM is React's way of minimizing expensive real-DOM operations. Every state/prop change produces a new VDOM tree, which React diffs against the previous tree, then patches only what changed in the real DOM."

**Common follow-ups:**
- *Is Virtual DOM always faster than direct DOM manipulation?* No — for very simple, targeted updates, direct DOM manipulation can be faster. VDOM's win is in **predictability and developer ergonomics at scale**, not raw speed for every case.
- *Does VDOM eliminate all reflows?* No, it minimizes unnecessary ones by batching and diffing.

## 2. Reconciliation (Diffing Algorithm, Keys)

**Reconciliation** = the process React uses to compare the new VDOM tree with the old one and determine the minimal set of DOM mutations needed.

**Diffing heuristics React uses (O(n) instead of O(n³)):**
1. **Different element types** → React tears down the old subtree entirely and builds a new one (no reuse of DOM nodes or state).
2. **Same element type** → React keeps the DOM node, only updates changed attributes/props, and recurses into children.
3. **Lists** → React uses **keys** to match children between renders instead of comparing by index.

**Why keys matter:**
- Keys give elements a **stable identity** across renders.
- Without keys (or using array index as key when list order changes), React may misattribute state to the wrong item, cause unnecessary re-mounts, or produce UI bugs (e.g., input values appearing on the wrong row after a reorder/delete).

**Interview trap question:** *"Why is using array index as a key bad?"*
> Because if items are reordered, inserted, or removed, the index no longer maps to the same logical item — React may reuse a DOM node/state for a different item than intended, causing stale UI or lost input focus. Index-as-key is acceptable only when the list is static and never reordered/filtered.

**Code snippet to have ready:**
```jsx
{items.map(item => (
  <ListItem key={item.id} data={item} /> // stable, unique id — not index
))}
```

## 3. Rendering Lifecycle

**Function component lifecycle (modern React, via hooks):**

| Phase | What happens | Hook equivalent |
|---|---|---|
| **Mounting** | Component created, inserted into DOM | `useEffect(() => {}, [])` |
| **Updating** | Re-render due to state/prop/context change | `useEffect(() => {}, [deps])` |
| **Unmounting** | Component removed from DOM | cleanup function returned from `useEffect` |

**Render phase vs Commit phase (important distinction interviewers probe):**
- **Render phase:** React calls your component function, builds the new VDOM, performs diffing. This phase is **pure** — no side effects, no DOM mutations. Can be paused/aborted/restarted (relevant to Concurrent Mode).
- **Commit phase:** React applies the computed changes to the real DOM, then runs `useLayoutEffect` (synchronously) and `useEffect` (asynchronously, after paint).

**Interview soundbite:**
> "Rendering doesn't mean the DOM updates immediately — render phase computes *what* should change, commit phase actually applies it. Effects run after commit, not during render, which is why side effects belong in `useEffect`, not in the component body."

## 4. Component Re-rendering

**A component re-renders when:**
1. Its own **state** changes (`useState`/`useReducer` setter called).
2. Its **parent re-renders** (by default, all children re-render too, regardless of whether their props changed).
3. **Context** it consumes changes value.
4. Force update (rare, class components only).

**Key nuance:** A re-render of a parent does **not** mean the child's DOM changes — React still diffs. But the child's **function body runs again**, which matters for expensive computations.

**Optimization tools (know these, and know their tradeoffs):**
- `React.memo` — skip re-render if props are shallow-equal.
- `useMemo` — memoize expensive computed values.
- `useCallback` — memoize function references (useful to keep `React.memo` children from re-rendering due to new function props).

**Interview trap:** *"Does `useMemo`/`useCallback` always improve performance?"*
> No — they have their own cost (storing deps, comparing them). Overusing them can add overhead without benefit. Use them when you've identified an actual expensive render or a referential-equality problem (e.g., preventing a memoized child from re-rendering).

## 5. State vs Props

| | State | Props |
|---|---|---|
| Owned by | The component itself | Parent component |
| Mutable? | Yes, via setter (`setState`/`useState`) | No — read-only from child's perspective |
| Triggers re-render? | Yes, when changed | Yes, when parent passes new values |
| Purpose | Internal, dynamic data | Configuration passed from outside |

**Interview soundbite:**
> "Props flow down and are immutable from the receiving component's side — a child should never mutate its own props. State is local and mutable, but only through the setter, never by direct mutation, because React relies on reference changes to know when to re-render."

**Common follow-up:** *"Can you derive state from props?"* Yes, but avoid storing a copy of a prop in state that then goes stale — prefer deriving values during render, or use `useEffect` with the prop as a dependency only when you truly need synchronized local state (an anti-pattern to be aware of: "state derived from props" bugs).

## 6. Controlled Components

The form element's value is **driven entirely by React state** — the DOM element has no memory of its own; it's a reflection of state.

```jsx
function ControlledInput() {
  const [value, setValue] = useState('');
  return (
    <input value={value} onChange={(e) => setValue(e.target.value)} />
  );
}
```

**Why controlled is usually preferred:**
- Single source of truth (state).
- Easy to validate, transform, or conditionally disable on every keystroke.
- Easy to reset/programmatically set.

---

## 7. Uncontrolled Components

The DOM itself holds the value; React reads it only when needed (typically via `ref`), not on every change.

```jsx
function UncontrolledInput() {
  const inputRef = useRef(null);
  const handleSubmit = () => console.log(inputRef.current.value);
  return <input ref={inputRef} defaultValue="hello" />;
}
```

**When to prefer uncontrolled:**
- Simple forms, file inputs (`<input type="file">` **must** be uncontrolled — its value can't be set programmatically for security reasons).
- Performance-sensitive cases where re-rendering on every keystroke is wasteful (e.g., large forms, or integrating with non-React code).

**Interview soundbite:**
> "Controlled trades a bit of performance for predictability and single-source-of-truth; uncontrolled trades a bit of control for simplicity and less re-rendering. File inputs are a hard case — they're always uncontrolled."

## 8. Lifting State Up

When two or more sibling components need to **share and stay in sync with the same data**, move that state to their **nearest common ancestor**, and pass it down via props (with a callback to update it).

```jsx
function Parent() {
  const [value, setValue] = useState('');
  return (
    <>
      <InputA value={value} onChange={setValue} />
      <DisplayB value={value} />
    </>
  );
}
```

**Interview soundbite:**
> "Lifting state up is React's answer to 'single source of truth' when sibling components need synchronized data — instead of duplicating state in each component, you hoist it to the lowest common parent and pass it down."

**Follow-up:** *"What if the tree gets deep and passing props becomes painful (prop drilling)?"* → Mention **Context API**, or state management libraries (Redux, Zustand, Jotai) as escape hatches — but note Context isn't a full replacement for lifting state; it's for widely-needed, relatively stable data (theme, auth, locale).

## 9. Composition vs Inheritance

React's official guidance: **favor composition over inheritance.** Inheritance hierarchies in UI frameworks tend to become rigid and hard to reason about; composition (passing components as props/children) is more flexible.

**Composition patterns to know:**

```jsx
// 1. children prop (containment)
function Card({ children }) {
  return <div className="card">{children}</div>;
}
<Card><Avatar /><Bio /></Card>

// 2. Specialization via props
function WelcomeDialog() {
  return <Dialog title="Welcome" message="Thanks for visiting!" />;
}

// 3. Render props / component-as-prop (less common with hooks now, but still asked)
function List({ renderItem, items }) {
  return items.map(renderItem);
}
```

**Interview soundbite:**
> "React discourages component inheritance because UI variations are usually about *what's rendered inside*, not *shared behavior via a class hierarchy*. Composition — passing components/children as props — models that far more naturally, and hooks now cover most of the code-reuse cases that inheritance or mixins used to handle."

## 10. Synthetic Events vs Native Events

**SyntheticEvent:** React's cross-browser wrapper around the browser's native event object. It normalizes event behavior across browsers and integrates with React's event delegation system.

**Key facts interviewers check:**
- React (pre-v17) attached a **single event listener at the document root** and used event delegation/bubbling to route events to the right component (event pooling). **React 17+ attaches listeners to the root DOM container** the app is rendered into, not `document`, which makes it easier to embed multiple React versions on one page.
- `event.nativeEvent` gives access to the underlying native event if needed.
- Event pooling (SyntheticEvent objects being reused/nullified after the handler runs) was **removed in React 17** — you can safely access event properties asynchronously now.

**Interview soundbite:**
> "SyntheticEvents give you a consistent API across browsers and let React manage event delegation efficiently instead of attaching a listener per DOM node. Under the hood you can still drop down to `nativeEvent` if you need browser-specific behavior."

## 11. Strict Mode (Why Effects Run Twice in Dev)

`<React.StrictMode>` is a **development-only** tool that helps surface potential problems. It doesn't render any visible UI and doesn't affect production builds.

**Why effects (and some other functions) run twice in dev under Strict Mode (React 18+):**
- React intentionally **mounts, unmounts, and remounts** components once extra in development to simulate what would happen if a component's state were **preserved and effects re-run**, in preparation for future features like the Offscreen API (reusable/cacheable component trees).
- This surfaces bugs where effects **aren't properly cleaned up** — e.g., subscriptions, timers, or event listeners set up in `useEffect` without a matching cleanup function.

**Interview soundbite:**
> "It's not a bug — it's Strict Mode intentionally double-invoking mount/unmount/mount in dev to catch effects that don't clean up after themselves. If your effect breaks when run twice, it means your cleanup function is missing or incomplete, and that bug would eventually bite you in production scenarios like fast navigation or component remounting."

**Follow-up:** *"Does this happen in production?"* No — Strict Mode's double-invoking behavior is dev-only; production builds render/effect once as expected.
